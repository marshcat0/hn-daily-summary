In software, AI can run and test code inside your computer in a matter of seconds. But as firmware engineers, we didn’t have that luxury. An AI agent can write firmware in seconds, but in order to test it, we had to flash a physical board, then manually run tests using expensive and clunky tools with software made over a decade ago.<p>To speed up the validation loop, we built the simulation layer that lets AI agents test the firmware and make decisions based on evidence, instead of waiting for the engineer to run tests for them. We used to spend hours testing our firmware manually on devboards, but now we use our own simulation to validate firmware in seconds.<p>What we offer:
- Virtual devboards you can program and run with a single API call, without leaving your terminal.
- An AI code reviewer for firmware, that makes informed decisions based on evidence, using our simulation as a verification engine.
- A CI&#x2F;CD pipeline for your hardware projects that validates your firmware against a simulated version of the microcontroller on every commit.<p>Here is a demo of our simulation used in an AI code review session: <a href="https:&#x2F;&#x2F;www.youtube.com&#x2F;watch?v=kBK1ZjGWWbQ" rel="nofollow">https:&#x2F;&#x2F;www.youtube.com&#x2F;watch?v=kBK1ZjGWWbQ</a><p>Our users are using Simantic for bare-metal and RTOS development for applications like flight controllers, electric vehicles, robotics, and satellites. We built our MVP that was essentially a wrapper around Renode, but we quickly realized there were a lot of limitations to doing this.<p>1. We were bottlenecked by the development speed of Renode themselves. We tried making contributions on Github to fix issues we came across, but the speed in which we could merge our features in was not fast enough for a startup like us trying to move fast.<p>2. Renode is built using Dotnet, and it was proving itself to be slower than we would have liked. Renode was released in 2017, which was when all code was still being written by hand, so I think it made sense looking back, but there were limitations because of the language itself.<p>3. The open source tools were bloated, with features that we would never use. Yes, there were a  breadth of features, but we had a lot of things we had to work around just because we couldn’t remove or change them.
Users were complaining about simulation accuracy. ## 一、AI 产品设计的反思与批判（4 篇）

这一组是今日最集中的议题：AI 功能正在从“卖点”变成“负担”，设计师开始反思如何让 AI 真正服务于人。

**1. Nobody asked for the sparkle button**
核心观点：产品千篇一律地塞入 AI 面板，用户却在到处找关闭按钮，投入已超过回报。作者主张“用 AI 构建功能，而不是构建 AI 功能”——这是对当前 AI 功能堆砌潮最直接的批评。
值得关注：为 AI 产品设计提供了反主流视角的警醒。
链接：https://uxdesign.cc/nobody-asked-for-the-sparkle-button-ae54ab5065c6

**2. On giving people an undo button in AI products**
核心观点：AI 编辑应可检查、可接受、可回退，且不丢失用户想保留的内容。“撤销”是 AI 产品信任设计的关键机制。
值得关注：把“可恢复性”作为 AI 交互设计的核心原则，具有很强的可操作性。
链接：https://karlkoch.me/writing/on-giving-people-an-undo-button-in-ai-products

**3. The software factory forgot about design**
核心观点：代码变便宜了，但“决定做什么、以及它该有什么感觉”依然昂贵——这正是“软件工厂”模式缺失的部分。
值得关注：在 AI 加速生产的语境下，重新论证设计决策的稀缺价值。
链接：https://atifaz.am/writing/the-software-factory-forgot-about-design

**4. Microsoft's identity for Copilot positions it as a tool for work**
核心观点：通过动态运动几何重塑 Copilot 品牌识别，把软件逻辑转译为“企业生产力”的视觉语言。
值得关注：大厂如何用品牌设计为 AI 产品定位，是品牌视觉与产品策略结合的案例。
链接：https://the-brandidentity.com/project/microsofts-identity-for-copilot-positions-it-as-a-tool-for-work


## 二、设计系统与工程性能（2 篇）

**5. Design systems should be fast by default**
核心观点：如果设计系统的组件交互缓慢，那么所有基于它构建的应用都会慢。性能应成为设计系统的默认属性。
值得关注：把性能纳入设计系统的“设计责任”，打通设计与工程的边界。
链接：https://denodell.com/blog/design-systems-should-be-fast-by-default

**6. Code review was never about the code**
核心观点：代码评审本质上是验证步骤——代码是否产生了我们想要的结果，而非纠结代码本身。
值得关注：虽偏工程管理，但与“设计评审”的逻辑相通，对设计协作流程有借鉴意义。
