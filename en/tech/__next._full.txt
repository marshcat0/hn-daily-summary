### 综合分析：今日技术热点

今日的技术新闻呈现出一个非常有趣的格局：**开发者工具与平台的信任危机** 成为绝对的核心议题，围绕 GitHub 的“离开”与“依赖”形成了激烈的讨论。同时，编程语言的哲学之争、AI 工具的实用性问题以及硬件/基础设施的深度报道也构成了重要组成部分。

### 按子主题分组

#### 1. GitHub 的信任危机与开源生态的未来

这个主题是今日热度最高的焦点，多篇文章从不同角度探讨了对 GitHub（及其母公司微软）的依赖和担忧。

- **Ghostty is leaving GitHub**
    - **说明**: 终端模拟器项目 Ghostty 的作者宣布将项目从 GitHub 迁移出去。这是对 GitHub 平台（尤其是 Copilot 和 Actions）日益增长的控制权和商业化的直接回应，引发了关于开源项目自主性的广泛讨论。这是今日最重磅的新闻之一。
    - **文章**: https://mitchellh.com/writing/ghostty-leaving-github
    - **讨论**: https://news.ycombinator.com/item?id=47939579

- **Before GitHub**
    - **说明**: 这篇文章回顾了 GitHub 出现之前的开源协作生态（如邮件列表、SVN等），为理解当前对 GitHub 的依赖提供了一个历史视角。与 Ghostty 离开的新闻形成鲜明对比和背景补充。
    - **文章**: https://lucumr.pocoo.org/2026/4/28/before-github/
    - **讨论**: https://news.ycombinator.com/item?id=47940921

- **We need a federation of forges**
    - **说明**: 文章提出了一个解决方案：建立一个由多个代码托管平台（Forge）组成的联邦（如基于 ForgeFed 协议），以避免对单一平台（GitHub）的过度依赖。这与 Ghostty 的离开和“Before GitHub”的回顾构成了一个完整的讨论闭环。
    - **文章**: https://blog.tangled.org/federation/
    - **讨论**: https://news.ycombinator.com/item?id=47948603

- **GitHub Actions is the weakest link**
    - **说明**: 文章警告 GitHub Actions 的安全风险，指出其工作流可能被利用作为攻击向量，成为整个软件供应链的薄弱环节。这加剧了对 GitHub 平台安全性的担忧。
    - **文章**: https://nesbitt.io/2026/04/28/github-actions-is-the-weakest-link.html
    - **讨论**: https://news.ycombinator.com/item?id=47933257

- **GitHub Copilot code review will start consuming GitHub Actions minutes**
    - **说明**: 这一公告意味着使用 Copilot 代码审查功能将开始消耗 Actions 的免费额度。这被许多人视为 GitHub 将其 AI 功能货币化、进一步锁定用户的举措，也是导致上述信任危机的原因之一。
    - **文章**: https://github.blog/changelog/2026-04-27-github-copilot-code-review-will-start-consuming-github-actions-minutes-on-june-1-2026/
    - **讨论**: https://news.ycombinator.com/item?id=47932028

- **Soft launch of open-source code platform for government**
    - **说明**: 荷兰政府推出了自己的开源代码平台。这可以看作是对“forge 联邦”理念的一种实践，表明政府机构也开始寻求 GitHub 之外的替代方案。
    - **文章**: https://www.nldigitalgovernment.nl/news/soft-launch-for-government-open-source-code-platform/
    - **讨论**: https://news.ycombinator.com/item?id=47945918

    - **讨论**: https://news.ycombinator.com/item?id=47949939

I hacked this project together last weekend, inspired by the Codex Computer-Use release and lessons learned from deploying GUI-operating agents for our customers.<p>The main problem: when a UI automation process controls a desktop app today, it usually takes over the human’s session. Your cursor moves, keyboard focus gets stolen, windows jump to the front, and you have to stop working until the agent is done. That is why we have historically avoided encouraging users to run these processes directly on their host machine, instead relying on VMs or GUI containers for concurrency and background execution.<p>But computer-use - the tools we give agents to operate computers like humans - does not scale cleanly that way. As models get smarter, agents need to share hosts safely, run in the background, and avoid collisions with the human or other agents using the same machine.<p>We realized macOS has no first-class API for &quot;drive this app without touching the cursor&quot;. CGEventPost routes through the hardware input stream, so it moves your cursor. CGEvent.postToPid avoids the cursor warp, but Chromium treats those events as untrusted and silently drops clicks at the renderer boundary. Activating the target app first raises the window and pulls focus, defeating the point of background execution.<p>Cua Driver is our attempt at a real fix: a background computer-use driver for macOS that lets an agent click, type, scroll, and read native apps while your cursor, frontmost app, and Space stay where they are. The default interface is a CLI, so it is easy to script or call from any coding agent shell.<p>Try it on macOS 14+:<p>&#x2F;bin&#x2F;bash -c &quot;$(curl -fsSL <a href="https:&#x2F;&#x2F;raw.githubusercontent.com&#x2F;trycua&#x2F;cua&#x2F;main&#x2F;libs&#x2F;cua-driver&#x2F;scripts&#x2F;install.sh" rel="nofollow">https:&#x2F;&#x2F;raw.githubusercontent.com&#x2F;trycua&#x2F;cua&#x2F;main&#x2F;libs&#x2F;cua-d...</a>)&quot;<p>The first internal use case was delegated demo recording. We ask Claude Code to drive an app while &#x27;cua-driver recording start&#x27; captures the trajectory, screenshots, actions, and click markers. The result is an agent-generated product demo, Screen Studio inspired.<p>Other things we have used it for:<p>- Replacing Vercel’s agent-browser and other browser-use CLIs. With Claude Code and Cua Driver, you do not need Chrome DevTools Protocol at all.<p>- A dev-loop QA agent that reproduces a visual bug, edits code, rebuilds, and verifies the UI while my editor stays frontmost.<p>- Personal-assistant flows that use iMessage from Claude Code, Hermes, or other general-purpose agent CLIs.<p>- Pulling visual context from Chrome, Figma, Preview, or YouTube windows I am not looking at, without relying on their APIs.<p>What made this harder than expected:<p>- CGEventPost warps the cursor because it goes through the HID stream.<p>- CGEvent.postToPid does not warp the cursor, but Chromium drops it at the renderer IPC boundary.<p>- Activating the target first raises the window and can drag you across Spaces.<p>- Electron apps stop keeping useful AX trees alive when windows are occluded without a private remote-aware SPI.<p>The unlock was SkyLight. SLEventPostToPid is a sibling of the public per-PID call, but it travels through a WindowServer channel Chromium accepts as trusted. Pair it with yabai’s focus-without-raise pattern, plus an off-screen primer click at (-1, -1), and the click lands without the window ever raising.<p>One thing we learned: the right addressing mode depends on the app. Native macOS apps usually have rich AX trees, Chromium-family apps often need a hybrid of AX and screenshots, and apps like Blender or CAD tools may expose almost no useful AX surface. The mistake is defaulting to pixels everywhere - or defaulting to AX everywhere.<p>Long technical writeup: <a href="https:&#x2F;&#x2F;github.com&#x2F;trycua&#x2F;cua&#x2F;blob&#x2F;main&#x2F;blog&#x2F;inside-macos-window-internals.md" rel="nofollow">https:&#x2F;&#x2F;github.com&#x2F;trycua&#x2F;cua&#x2F;blob&#x2F;main&#x2F;blog&#x2F;inside-macos-wi...</a><p>I would like feedback from people building Mac automation, agent harnesses, or accessibility tooling.
